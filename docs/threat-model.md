# Threat Model

This kit stops keygens, casual key sharing across more than `MAX_SEATS + SEAT_RELEASES_PER_YEAR` Macs per year, and unpaid or refunded Stripe sessions without requiring user accounts or background check-ins.

## Handled

### Keygens and forged tickets
`LicenseTicket.verify` checks the 64-byte Ed25519 signature over the raw payload bytes before decoding UTF-8 or splitting fields. There is no unsigned or fallback parser path.

### Sharing one purchase across many Macs
Each purchase key maps to a SQLite Durable Object (`SeatCoordinator`, named `lic:<sha256(domain + key)>`). Seat changes run inside `ctx.storage.transactionSync(...)`. Minted tickets include the Mac's 16-hex `deviceSeatCode` (`SHA256(seatHashDomain + IOPlatformUUID)[0..<8]`), so copying `.license_vault` to another Mac fails offline with `.seatMismatch`.

### Copy ticket -> Deactivate -> re-paste offline
A common flaw in offline ticket systems: a user activates Mac A, copies the signed `LK1-` ticket out of storage, clicks Deactivate (freeing the seat on the server for Macs B and C), and pastes the old `LK1-` ticket back into Mac A offline.

- Client side: `SeatStampManager.deactivate()` sets `seatRevokedBeforeEpoch` to at least `releasedTicket.issued + 1`, and up to the current clock but never more than 365 days past the released ticket, in all HMAC-sealed local anchors before clearing the ticket. Any seat-bound ticket with `issued < seatRevokedBeforeEpoch` is rejected offline on that Mac (`Failure.revoked`) until the server issues a newer ticket. This protects an install whose `deactivate()` ran. It does not reach a Mac whose seat was released by a direct `deactivate` request or by eviction: that Mac keeps working offline until it runs `deactivate()` or installs a build that revokes its order tag. The Worker therefore caps releases at `SEAT_RELEASES_PER_YEAR` (default `MAX_SEATS`) per rolling 365 days and answers `429 release_limit` beyond that, which bounds one purchase to `MAX_SEATS + SEAT_RELEASES_PER_YEAR` Macs per year.
- Server side: `SeatCoordinator` soft-releases deactivated seats (`deactivated_at = now`), updates a monotonic `revoked_before` watermark on the record, and sets `issued = max(now, revoked_before + 1, min(minIssued, now + 366 days))` on every newly minted ticket. `minIssued` is the app's sealed cutoff, sent with `activate` and `claim_checkout`. The app checks every ticket, including one that arrives in a server response, against its sealed cutoff and never lowers the cutoff, so replaying an old ticket through a TLS-intercepting proxy fails with `.clockSkew`. A buyer who asks the Worker directly for a ticket dated ahead (through `minIssued`) and pastes it after Deactivate is in the same position as one who releases the seat with a direct request; the release budget bounds both.

### Unauthenticated seat deactivation
`deactivate` requires presenting the signed `LK1-` Ed25519 ticket minted for `(scheme, orderTag, seat)`. Knowing or guessing someone's purchase key does not let an attacker remotely free their seats.

### Unpaid, test-mode, subscription, refunded, or disputed Stripe sessions, and wrong-product purchases when product scoping is configured
- With a live Stripe key (`sk_live_...` or `rk_live_...`), `cs_test_...` keys and `livemode !== true` sessions are rejected.
- Non-`payment` Checkout modes (`subscription`, `setup`) are rejected.
- Product scoping is off by default. A purchase of another product on the same Stripe account is rejected only when you set `STRIPE_ALLOWED_PAYMENT_LINKS` (Stripe `plink_...` IDs). Set it before you add a second product or Payment Link to the account.
- Stripe leaves `session.payment_status` set to `"paid"` after a full refund or chargeback. The Worker requests `?expand[]=payment_intent.latest_charge` and checks `latest_charge.refunded` and `amount_refunded >= amount`. When `latest_charge.disputed` is true it lists the disputes of the PaymentIntent: all `won` or `warning_closed` keeps the order valid, any `lost` or `prevented` rejects it and wipes the record, and an open dispute refuses new seats with `403 payment_disputed` without wiping anything.
- If the restricted Stripe key lacks `PaymentIntents: Read` or `Charges: Read` (`403`), if `latest_charge` is missing on a paid session, or if Stripe returns `429`, `5xx`, or any other unexpected status except `404` (for example `400` after an API change), the Worker returns `502` rather than skipping the refund check, and it never wipes a record on such an answer. If an existing key is later refunded, the next activation attempt that reaches Stripe (any new seat, or an existing seat more than one hour after the last check), or a `/thank-you` load for that key, makes the Worker call `deleteAll()` on the Durable Object and negative-cache the key hash. An existing seat is re-issued without a Stripe answer only inside that hour, or while Stripe is unreachable and the last successful check is less than 30 days old; a rate-limited check returns `429` for every seat.

### Server compromise pushing malicious updates
`license-tool` generates two separate Ed25519 keypairs:
1. License key: stored in Cloudflare Worker secret `ED25519_PKCS8_B64` to mint seat tickets.
2. Update key: kept offline on your Mac; signs `version.json` over a length-prefixed canonical byte stream (`UpdateManifest.canonicalSigningData`), and `UpdateChecker` pins HTTPS download hosts and path prefixes (rejecting `..` path traversal). When you sign with `license-tool --sign-manifest version.json --artifact MyApp.dmg`, the signed bytes also contain the SHA-256 and size of the file, and `downloadAndVerifyUpdate()` deletes a download that does not match.

If your Cloudflare account is compromised, an attacker can mint license tickets until you rotate the license key (see the section Key rotation and compromise recovery below), but cannot sign a malicious update manifest. What the signature protects: the notice, the URL, and (when present) the hash of the file. A manifest without `sha256` does not bind the file, so an attacker who controls the download host can replace it; sign every release with `--artifact`.

### Key rotation and compromise recovery
1. Secure the account first: change the Cloudflare password, revoke API tokens, and roll the Stripe restricted key.
2. Run `swift run license-tool --scheme MYAPP-V1 --rotate-keypair`. The old private key is archived next to the new one and is never overwritten.
3. Upload the new secret with `wrangler secret put ED25519_PKCS8_B64`. If you set the variable `ED25519_PUB_B64`, change it to the new public key in the same deploy, or delete it. Set the Worker variable `ED25519_RETIRED_PUB_B64` to the old public key, so Macs that still hold an old ticket can release their seat. From this moment builds that trust only the old key cannot complete a new activation until they update; Macs that are already activated keep working.
4. Ship an app update the same day with `licensePublicKeyBase64` set to the new key and `retiredLicensePublicKeysBase64` set to a list that holds the old public key. On first launch the update keeps each buyer licensed for `retiredKeyGraceDays` (default 30) and re-activates in the background with the stored purchase key on the same seat. A forged ticket with a forged purchase key stops at once when the Worker answers `invalid_key`. A forged ticket without a purchase key, or one that a user writes into `.license_vault`, keeps working in every build that lists the old key as retired, until step 5.
5. After the grace period ship a release with an empty retired list, and remove `ED25519_RETIRED_PUB_B64` from the Worker (Macs that still hold an old-key ticket then cannot release their seat online).

Limits: the grace start is stored in `.license_vault`, so a user who edits that file can restart it until step 5; builds that never update keep accepting old-key tickets; a ticket minted with `license-tool --mint` has no purchase key and must be minted again with the new key; the update key has no rotation path, so keep it offline.

### Offline revocation of refunded or chargebacked orders
Each minted ticket carries a deterministic 64-bit order tag (`ORD-<16-hex>`, the first 8 bytes of `SHA256(keyHashDomain + purchaseKey)`). Shorter 8-hex `ORD-` tags are also accepted.
- In new app releases (`SeatStampManager(revokedOrderTags:)`): pass a set of revoked `ORD-...` tags (derived offline with `swift run license-tool --tag-for-key cs_live_...`). `LicenseTicket.verify` rejects any seat-bound or universal ticket whose normalized tag is in `revokedOrderTags` (`Failure.revoked`), while leaving `deviceSeatCode` and `TrialSeal` untouched so a legitimate re-purchase (`ORD-NEW...`) on the same Mac activates cleanly.
- In signed `version.json` manifests (`revoked_tags`): run `swift run license-tool --scheme MYAPP-V1 --revoke-key cs_live_... version.json` to add the derived `ORD-` tag to `revoked_tags` and sign it with your offline update key. When `revoked_tags` is empty, `UpdateManifest.canonicalSigningData` omits that section; when non-empty, `revoked_tags[<count>]` and each sorted length-prefixed tag are included in the Ed25519-signed byte stream, so a CDN cannot add a revocation or edit the list. A manifest signed with `--seq` also carries a signed `manifest_seq`. A 2.x client stores the highest value it accepted and rejects any manifest with a lower one, so a host cannot replay an older signed manifest to a client that already saw a newer one. A client that never saw the newer manifest, and every 1.x client, can still be served the old one. Once you publish a manifest with `manifest_seq`, every later manifest at that URL must carry a higher one: always sign it with `--seq` (or `--artifact`), or 2.x clients reject it.
- Configurable client behavior (`UpdateChecker.RevocationBehavior`):
  - `.suppressUpdates` (default): hides update notifications when `kit.orderTag` is in `revoked_tags` while leaving the currently installed binary working.
  - `.revokeLocalLicense`: immediately deactivates the local license (`kit.isLicensed = false`) and persists the revoked tag in `.license_vault` so offline relaunches also reject the revoked ticket. The stored set mirrors the newest manifest that carries a `manifest_seq`: to undo a revocation run `swift run license-tool --scheme MYAPP-V1 --unrevoke-key cs_live_... version.json` and publish the file. A 2.x client then forgets the tag on its next check, and the buyer activates again with the same key. Tags passed to `SeatStampManager(revokedOrderTags:)` in a release cannot be undone. A 1.x client never forgets a tag, but after it updates to 2.x it keeps only the tags in the newest sequenced manifest.

### System clock rollback and wrong-clock trial expiration
- Trial timestamps (`first`, `high`, `revokedBefore`) are HMAC-SHA256 sealed with a hardware-derived key across `UserDefaults`, `~/Library/Application Support/<bundleID>/.vault_seal`, `~/Library/Caches/<bundleID>/.vault_seal`, and the macOS Keychain (when signed with a valid Apple Developer Team ID). The seal key is derived from the hardware UUID and the bundle ID, which are not secret, so the seal stops casual edits and file copies and does not stop a user who recomputes it.
- Deleting `UserDefaults` or running a preference cleaner self-heals from the surviving anchors.
- Rolling the system clock backward, while the app runs or before a launch, does not extend the trial (`effectiveNow = max(now, highWaterEpoch)`). The sealed `first` and `high` values are never lowered.
- Rolling the system clock forward by months or years does not permanently expire a trial: `highWaterEpoch` advances by at most +7 days per launch and by at most +7 days per hour while the app runs, so a launch under a wrong future clock costs at most 7 trial days, and a stored mark is kept when the clock is corrected.

### Browser CSRF, oversized streams, and session-ID probing
- `POST /` rejects any request carrying an `Origin` header or `Sec-Fetch-Site: cross-site` (`403 forbidden_origin`) before reading the body.
- Request bodies are read via a bounded stream reader (`2048` bytes max) that aborts mid-stream without trusting `Content-Length`.
- `/thank-you` enforces a `3 req/min/IP` rate limit (separate from `POST /`) and serves a per-response nonce CSP (`script-src 'nonce-...'`, no inline event handlers).
- Default-browser auto-activation (`beginBrowserCheckout` / `action: "claim_checkout"`) uses a 128-bit random `chk_<32-hex>` token passed as Stripe `client_reference_id`. The Worker hashes the token (`handoff:<sha256(keyHashDomain + "handoff|" + handoff)>`), verifies the Stripe Checkout Session through `verifyKeyWithStore` (including `livemode`, `STRIPE_ALLOWED_PAYMENT_LINKS`, and `payment_intent.latest_charge` refund/dispute checks), stores no direct identifiers (the handoff record holds the purchase key and the claiming Mac's seat code for up to 24 hours), and wipes the ephemeral handoff Durable Object after 24 hours via `ctx.storage.setAlarm(...)` (`deleteAll()`).
  - If the buyer closes the tab before `/thank-you` loads, the app's `fallbackSearch: true` claim makes the Worker list recent completed sessions (`GET /v1/checkout/sessions?status=complete&created[gte]=<24h ago>&limit=100`, one list per allowlisted `payment_link` when 1 to 8 links are allowlisted, at most 2 pages each, at most once per 15 seconds and 40 times per handoff, and only for a handoff the Worker first saw at least 30 seconds earlier) and match `client_reference_id`. Every candidate still goes through `verifyKeyWithStore`. A Stripe outage or a key lacking list permission returns `502 upstream_unavailable`, never a silent `202 pending`.
  - `claim_checkout` has its own `30 req/min/IP` budget (`"claim"` scope) so background polling cannot exhaust the `12 req/min/IP` activation budget.
  - The `chk_` token is a bearer credential until the first poll: the first seat code that polls a token is bound to it (`handoff_seat`), and every other seat code gets `403 handoff_seat_mismatch`. The buyer's app polls within seconds of opening checkout, so a token read later from browser history or the Stripe Dashboard is useless on another Mac. The claim response for the bound seat contains the `cs_live_` purchase key, so whoever makes the first poll with a stolen token before the app does receives the key. The token grants nothing after the handoff DO is wiped. `/thank-you` records a handoff only inside the thank-you window and at most 24 hours after payment, so reloading an old URL does not revive a wiped handoff.
- Email key recovery (`action: "recover"`) is designed so that the endpoint cannot be used to learn who bought the app:
  - Every well-formed email gets the same `200 { ok: true }` with identical headers, whether it matches a purchase, matches nothing, or was asked for a minute ago. The Stripe lookup and the Resend send run after the response inside `ctx.waitUntil`, so there is no timing difference either.
  - Per-email cooldown state lives in a `recover:<HMAC-SHA256(STRIPE_SECRET_KEY, domain + "recover|" + the trimmed address as typed)>` Durable Object holding only a timestamp, armed to `deleteAll()` after 15 minutes. Because the digest is keyed with the Stripe secret, a dump of DO names cannot be checked offline against a list of candidate addresses.
  - Abuse limits: 3 requests per IP per 10 minutes, at most 2 Stripe list calls per lookup (lowercase plus one casing variant), at most 5 keys per email, one Resend call per 15-minute window keyed by `Idempotency-Key`. The cooldown is per typed spelling; the `Idempotency-Key` uses the lower-cased address, so the provider still sends at most one email per address per window. A Stripe or provider failure releases the cooldown so the buyer can retry at once.
  - Residual risk: someone who controls the buyer's mailbox can obtain the key, which is also true of the Stripe receipt and the one-time `/thank-you` backup email. The email provider can also read the key in every message it sends for you and keeps it for 30 days. Someone who merely knows the buyer's address can make them receive at most one recovery email every 15 minutes.

## Non-Goals (What Is Left Unfixed)

### 1. Local binary patching
Anyone with Hopper, Ghidra, or `lldb` can patch the `verifyGateAccess()` branch in their local `.app` bundle or replace the 32-byte Base64 public key constant with their own keypair and re-sign ad-hoc (`codesign -fs -`).

Every offline native macOS app can be patched locally by its owner. Obfuscation, `PT_DENY_ATTACH`, and inline anti-debug checks break crash symbolication, cause notarization and endpoint-security issues, and are still routinely defeated. Security in this kit comes from your private Ed25519 keys, not from hiding the verification code.

### 2. Full 4-anchor trial reset or fresh macOS user / VM
Deleting all four local anchors (`UserDefaults`, `Application Support/<bundleID>/.vault_seal`, `Caches/<bundleID>/.vault_seal`, and the `<bundleID>.license-vault` Keychain item), or creating a new macOS user account or VM with a fresh `IOPlatformUUID`, starts a new 30-day trial. A first launch made with the clock set in the future delays the trial start by the same amount and belongs to this non-goal.

Preventing full local trial resets requires mandatory online registration before first launch, which hurts conversion and breaks offline first-time use.

### 3. Disabling an air-gapped Mac after a refund
Once Mac #1 has a signed `LK1-` ticket stored locally, `SeatStampManager` never makes mandatory license check-in calls. If that buyer gets a Stripe refund:
- The Worker refuses new Macs for that key from its next Stripe check: the next activation attempt, the next `/thank-you` load, or, for a Mac that is already activated, its first re-activation after the one-hour re-verification window. That same check wipes the seat record (`deleteAll()`). Until a request arrives for that key the record stays; `license-tool --erase-key` wipes it on demand.
- Adding the order's `ORD-` tag via `license-tool --revoke-key` suppresses updates (or revokes the local license under `.revokeLocalLicense`) on the next `version.json` check, and blocks the old ticket in any newly downloaded release (`revokedOrderTags`).
- However, if Mac #1 is kept offline (or has `autoCheckForUpdates = false`) and never installs a newer binary, that installed copy stays unlocked until deactivated or reinstalled.

Adding a mandatory periodic background heartbeat that bricks the app when unreachable would break legitimate buyers' Macs whenever they are offline or if your domain expires years later.

### 4. Per-isolate rate limits
The Worker's IP rate-limit maps, the negative cache, and the Stripe call budget (`PER_ISOLATE_STORE_MAX_CALLS` per 10 seconds) live in the memory of one isolate. No IP data is written to storage, and none of these limits is global: across many Cloudflare locations and isolates a distributed client can exceed them and use up your Stripe read quota and Durable Object requests. The seat cap lives in `SeatCoordinator` (SQLite Durable Object) and is not affected. For sustained floods add a Cloudflare rate-limiting rule that matches only POST requests to the path `/`. Never match `/thank-you`: Cloudflare Security Events record the client IP address and the query string, and that query string is the license key. Rules on your own domain do not cover the `workers.dev` hostname, so set `workers_dev` to `false` when you rely on them, and keep `preview_urls` off. The optional `POST_RATE_LIMITER` binding in `worker/wrangler.jsonc` adds an approximate, per-location limit inside the Worker.
